# 检索与索引重构计划

> 状态：计划，尚未实施。现状见 [TEXT.md](./TEXT.zh-CN.md)、[RAG.md](./RAG.zh-CN.md)。
>
> 标「待定」的条目在用户确认后再动手。

---

## 要解决的问题

1. **单位不一致。** 全文检索一文件一行，向量检索一块一行，融合和重排时被硬压成文件。只有全文命中的文件没有正文片段，重排只能看到文件名。
2. **向量索引借用摘录。** 摘录是给预览和全文检索用的，向量索引读它，导致摘录的上限同时决定索引覆盖范围。
3. **一个工具两种性质。** `search_assets` 既有本地零成本的关键词检索，也有要调嵌入和重排的语义检索，Agent 无法选择。
4. **中文检索不可用。** FTS5 的 `unicode61` 把连续中文当成一个词，搜「天气」找不到「今天天气很好」。

## 目标结构

| | 简单检索 `search_assets` | 深度检索 `deep_search_assets` |
|---|---|---|
| 单位 | 文件 | 块 |
| 数据源 | `assets_fts`：文件名、路径、属性、摘录、描述 | 块级全文 + 块向量 |
| 融合 | 无，单路排序 | RRF，只融合块 |
| 重排 | 无 | 有，输入永远是块正文 |
| 覆盖 | 所有文件 | 已索引的文件 |
| 模型 | 不需要 | Embedding、Rerank 均可选 |

三层数据，各管各的：

| 层 | 内容 | 上限 | 用途 |
|---|---|---|---|
| 原文 | 磁盘文件 | 无 | 事实来源 |
| 摘录 | `asset_metadata.data.text` | 256 KiB | Details 预览、简单检索 |
| 块 | `text_chunks` + 块级全文 | 读原文件前 1 MiB | 向量检索、深度检索 |

深度检索只搜块，不带文件级全文。没索引的文件用简单检索找。

不做向后兼容：`search_assets` 直接从混合变为只做简单检索，不留别名和过渡参数。

## 切块时机

切块和向量绑在一起，只在用户点 Embed、Agent 调 `embed_asset`，或图片 / 视频 / 音频描述成功后自动接着索引时发生。导入和打开库不切块。

- 原因：同步切块约 2 秒 / MiB，不适合对整库自动做；向量要调外部接口并产生费用，必须由用户主动触发。
- 后果：没点 Embed 的文件没有块，深度检索看不到它们，改用简单检索。没配 Embedding 模型就建不了块，深度检索也就用不了。
- 后续可选：把「切块 + 块级全文」与「向量」拆开，前者在摘录之后后台自动做（不需要模型），后者仍手动。需要先有后台、可取消、让出事件循环的任务机制，见 [TODO](../TODO.zh-CN.md)。

## 步骤 1：索引自己读原文件

- `TextEmbedService` 不再依赖 `EnrichmentService`，改为注入 `resolvePath`，由 `LocalCore` 传入 `library.getAssetFilePath`。
- 新常量 `TEXT_INDEX_LIMIT = 1 MiB`（字节），放在 `model/text-embed.ts`。读文件前 1 MiB，在 UTF-8 边界截断。
- 截断提示按 `asset.size > TEXT_INDEX_LIMIT` 判断，不增加数据库列。
- `TEXT_ENRICHMENT_LIMIT` 回到 256 KiB，`ENRICHMENT_VERSION` 回到 1，删除 `TEXT_SEARCH_LIMIT`。
- CSV 截断丢最后一行、JSON 截断退成纯文本，沿用现有逻辑。
- 测试：约 8 处 `new TextEmbedService(...)` 换新签名，文本用临时目录里的真文件。
- 文档：`TEXT`、`SCHEMA` 中英文更新输入来源和两个上限。

## 步骤 2：块级全文与中文分词

- 新增 FTS5 表，每个**子块**一行，与向量覆盖同一批块。
- 用触发器同步：`text_chunks` 的子块删除时自动删 FTS 行。验证过：`ON DELETE CASCADE` 级联删行**不会**自动清 FTS 表，但会触发 `AFTER DELETE` 触发器，所以资产被删、块被替换都不会残留，不必逐个核对 `removeAsset`、`replaceAssets`、`upsertAsset`。
- 排序用 FTS5 自带的 `bm25`；需要片段时用 `snippet`。
- 已有库：打开时块级全文行数与子块数不一致，就从 `text_chunks` 回填。
- 接口：`MetadataStore` 新增 `searchChunksFts(query, limit)`，SQLite 与内存两个实现。`NearestChildHit` 改名为 `ChunkHit`，全文与向量共用。

### 中文分词

FTS5 内置分词器里没有按单字或按词切中文的（`unicode61`、`ascii`、`porter` 都把连续中文当成一个词；`trigram` 要求至少 3 个字；`icu` 在当前 SQLite 里不可用）。方案是**用 `Intl.Segmenter` 先分词，再把结果交给 `unicode61`**，不换分词器（已定）：

- 写入时：连续的 CJK 文本交给 `new Intl.Segmenter("zh", { granularity: "word" })`，取 `isWordLike` 的词，用空格连接（`今天天气很好` → `今天 天气 很好`）。英文和数字不变，`unicode61` 照常工作。
- 查询时：同一个函数先给查询里的 CJK 段分词，每段编成一个短语（`"天气"`、`"人工 智能"`），保证词序和相邻；非 CJK 词仍是 `"word"*`，整体 AND。
- 分词函数独立成模块，存储层与查询共用。同一个 Segmenter 实例复用。
- 日文、韩文走同一个函数：日文用 `ja`、韩文用 `ko` 的词典分词会更准，但本次不区分语言，统一用 `zh`（未验证对日韩的效果，只确认了切得动）。
- **文件级全文 `assets_fts` 同样改用这个函数**（已定）。
- **用版本号触发重建。** 现在 `assets_fts` 只在「`assets` 与 `assets_fts` 行数不一致」时重建，换分词规则后行数不变，不会触发。因此在库里存一个「全文索引格式版本」（SQLite `PRAGMA user_version` 或一张小表）：打开库时版本落后就重建 `assets_fts` 并回填块级全文，写入新版本号。以后再改分词也用同一个办法。
- 测试：词、长词内部的词、中英混排、词序、中文文件名；块被替换、资产被删后搜不到旧内容；回填；旧版本号的库打开后被重建，版本已是最新时不重复重建。

### 中文分词的后果

用本机真实中文文档（22,682 个段落，约 420 万字符，其中汉字 155 万，占 37%）实测，真实 FTS5：

| 做法 | 索引体积 | 搜完整的词：召回 | 搜完整的词：精度 | 搜任意片段：召回 |
|---|---|---|---|---|
| 不处理（现状） | 19.7 MB | 0.30 | 1.00 | 0.20 |
| 单字拆开 + 短语 | 24.8 MB（+26%） | 1.00 | 0.999 | 1.00 |
| **`Intl.Segmenter`（本方案）** | **20.7 MB（+5%）** | **0.97** | **1.00** | **0.42** |
| Segmenter + 长词子词 | 20.9 MB（+6%） | 0.98 | 1.00 | 0.43 |

「完整的词」是用 Segmenter 从文本里取出的 2 到 4 字词；「任意片段」是随机截取的 2 到 4 字子串，常跨词。

采用本方案的后果：

1. **只能按词搜，不能按任意片段搜。** 搜完整的词几乎等同单字拆开；搜跨词的片段（如「气很好」）约一半找不到，因为索引里没有这个串。真实用户很少搜这种片段，但「文件名里的一段」「专有名词的一部分」会受影响。
2. **长词内部的短词可能搜不到。** `研究生院` 被切成 `研究生 / 院`，搜「研究」找不到它。补长词子词几乎没有提升（0.97 → 0.98），所以不做。
3. **索引只比现状大约 5%。** 英文、代码、标点不受影响。之前用纯中文合成文本估的「3.8 倍」偏高，真实文档里汉字只占约 37%。
4. **精度高。** 不会命中「大天气」这类跨词的相邻两字。
5. **依赖运行环境的 ICU 版本。** 切法由 ICU 词典决定。实测 Electron 38（ICU 74.2）与 Node 26（ICU 78.3）在六个例子上切法一致，但不同版本对生词、专有名词的切法可能不同。升级 Electron 后旧索引与新查询可能不一致。对策：把 ICU 版本（`process.versions.icu`）并入全文索引格式版本；版本变了就重建。
6. **一次性重建。** 升级后第一次打开库要重建 `assets_fts`（清空，再为每个文件重新拼出文件名、路径、属性、摘录、描述并写回）；块级全文对已索引文件从 `text_chunks` 回填。文件多、文本长时有一次性的耗时，且发生在打开库的路径上，期间检索不可用或不完整。分词本身很快（17.5 万字约 19 毫秒）。
7. **日文假名、韩文**统一用中文词典分词，切得动但不一定准，且日文常会切成单个假名。
8. **存储格式不兼容。** 旧的 `assets_fts` 内容与新分词不兼容，必须重建；回退版本后旧版本读到新格式的表会匹配出错。

备选与不选的理由：

- 单字拆开：召回最稳、不依赖 ICU，但索引大约 +26%，且会命中跨词相邻字（精度 0.97）。本次不选；若实际使用中发现「搜片段」是常见需求，可退回这个方案。
- `trigram`：两个字的词搜不到。
- 相邻两字（bigram）：更大，且搜不到单字。
- 分词库（词典随包发布）：切法与 ICU 版本无关，但词典大、打包与签名成本高。
- 自写 FTS5 分词器扩展：需要编译原生代码，跨平台打包成本高。

## 步骤 3：拆检索、工具、提示、文档

- **core**：`searchLibrary` 拆成两个方法。
  - `searchAssets`：文件级全文 + 类型、属性过滤；无 query 时仍是列表；去掉向量、RRF、重排、关系扩展。
  - `deepSearchAssets`：块级全文 + 块向量 → RRF → 过滤 → 重排块正文 → 每个文件取最佳块 → limit。没有 Embedding 槽时只有全文一路。
  - 返回 `indexedCount`（已索引文件数）。为 0 时 Agent 知道该改用简单检索或先建索引。
- **工具**：`search_assets` 改为简单检索；新增 `deep_search_assets`。嵌入、重排 provider 只给深度检索。
- **提示与引用**：`agent-prompt.ts` 写清何时用哪个；`asset-refs.ts` 两个工具名都产生可点击引用；确认 `run_retrieve_agent` 的工具集包含两者（组装位置待查）。
- **删除关系扩展**（已定）：检索不再沿关系走一跳，两个检索都没有 `linkedFrom` 行。
  - 删除：`retrieval/graph.ts`（`expandSearchCandidates`、`SEARCH_NEIGHBORS_PER_SEED`）；`model/retrieval.ts` 的 `linkedFrom` 与 `SearchLink`，以及 `core/src/index.ts` 的导出；`local-core.ts` 里的调用；`asset-tools.ts` 工具描述里关于 `linkedFrom` 与关系的句子；`packages/agent/src/extensions/specialist.ts` 检索专家提示里「search row has linkedFrom」那一句。
  - 保留：关系本身（图谱视图、Details 里的关系、`create_relation` / `remove_relation`、`inspect_asset` 返回的关系）。想看邻居时，Agent 用 `inspect_asset`。
  - 提示词补一句：命中后，需要溯源时对重要结果调用 `inspect_asset` 查看关系。
- **测试**：`graph-retrieval.test.ts` 整个删除（五个用例都是关系扩展）；`hybrid-search`、`retrieval`、`asset-tools`、`agent-prompt`、`asset-refs` 随新工具调整；`core/evals/retrieval.ts` 改调 `deepSearchAssets`。
- **文档**：`RAG`、`TEXT`、`SCHEMA`、`AGENT`、`PRODUCT` 中英文。`PRODUCT` 第 3.3 节里「搜索时每个候选沿关系走一跳」改为图谱只用于记录、浏览和 `inspect_asset`；`TEXT` 里关系扩展的整段删掉。

## 待定

无。

## 关系扩展删除的后果

- 少了一步到位的邻居发现：以前一次搜索就返回命中和它的邻居，现在 Agent 要对命中的文件再调 `inspect_asset`，命中多时调用次数增加。
- 与文本不相似、只靠关系关联的文件（例如描述里没提「海报」的源视频）不再自动出现在检索里，只有 Agent 主动沿关系去查才会看到。向量和全文检索替代不了这一点。
- `PRODUCT` 里「Creative Asset Graph」在检索端的体现被去掉，图谱变成记录与浏览。
- 后续若需要，可以加 `related_assets(assetId)` 一次返回邻居，或给 `deep_search_assets` 加默认关闭的 `includeRelated` 开关；本次不做。

## 风险与未验证

- 同步切块约 2 秒 / MiB，1 MiB 上限意味着单次索引最多停约 2 秒，会卡主进程。本次不解决；后续可放 worker 或分片让出事件循环。
- 超过 1 MiB 的 JSON 因截断解析失败，退化成纯文本，不展开成 `路径: 值`。
- 已验证：better-sqlite3 自带 SQLite 3.53.4，FTS5 的 `bm25`、`snippet` 可用；级联删除会触发 `AFTER DELETE` 触发器。
- 已量：中文分词的体积与召回见「中文分词的后果」；Electron 38 与 Node 26 的 `Intl.Segmenter` 在六个例句上切法一致。
- 未量：重建 `assets_fts` 与回填块级全文在大库上的耗时。重建发生在打开库时，慢了会拖慢打开；必要时改成后台进行并在完成前先用旧表。
- 未验证：中文文件名、路径被分词后对现有检索排序的影响；日文、韩文的分词效果；语料只用了一份偏技术的中英混排文档，纯文学、新闻、聊天记录的结果可能不同。
